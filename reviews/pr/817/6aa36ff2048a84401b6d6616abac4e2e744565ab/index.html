#815 fix(runtime): make canonical Runtime Appliance UEFI/GPT bootable under Lima (open)

Acceptance criteria

  • [ ] UEFI is encoded as the canonical boot contract for the Runtime Appliance used by Route 3; no `firmware.legacyBIOS=true` workaround is introduced into the Lima spec.
  • [ ] `nix/runtime-appliance-image.nix` builds the canonical raw appliance with an EFI-capable GPT layout (`partitionTableType = "efi"` or an equally explicit UEFI-only nixpkgs-supported layout), including a FAT32 ESP.
  • [ ] The appliance NixOS configuration installs a UEFI-capable bootloader rather than BIOS GRUB to `/dev/vda`; if GRUB is retained, it uses EFI support with `device = "nodev"` and a firmware-discoverable removable/fallback installation path suitable for a fresh VM without pre-existing EFI variables.
  • [ ] The image remains a self-bootable single-disk appliance and does not require externally supplied kernel/initrd flags.
  • [ ] The canonical `nixosModules.runtime` remains the sole guest semantic authority; this change is limited to appliance delivery/bootloader/partition concerns.
  • [ ] Route 3 continues to let Lima own QEMU command construction, firmware selection, VM lifecycle, device topology, and provider internals.
  • [ ] Route 4's verified edk2/QEMU binding remains the firmware/toolchain identity consumed by Lima; no unrelated ambient firmware/runtime is silently substituted.
  • [ ] Regression coverage proves the built appliance uses GPT + ESP and that its bootloader configuration is UEFI-compatible; legacy MBR-only output must fail the test.
  • [ ] Existing appliance boundary/golden-path Nix checks continue to pass and are updated where necessary to assert the UEFI image contract.
  • [ ] A fresh Route 3 convergence using an unmodified release descriptor reaches guest SSH on real Linux x86_64 KVM hardware and subsequently reaches `managedRuntimeReady=true`.
  • [ ] Re-run the #261 Route 3 certification step with the corrected canonical appliance and record the exact appliance identity used.
