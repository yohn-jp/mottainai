# Mottainai 0.7.0

Mottainai 0.7.0 established the first canonical Linux Runtime Appliance and
hardened the bounded runtime contracts around it. The release separated the
npm CLI/MCP package from a reproducible NixOS appliance that could be
transported independently to VM providers such as Proxmox. The current
bootstrap-only appliance boundary is defined by #627 and supersedes the
historical full-stack appliance wording below.

## Canonical Runtime Appliance

The 0.7.0 Nix flake exposed a self-bootable x86_64 Linux Runtime Appliance
built from the same runtime module used by the supported NixOS path. That
historical release snapshot composed the then-current application stack behind
one reproducible Nix closure; it is not the current base-appliance contract.
The current appliance contains the stable substrate and #626
`mottainai-bootstrap`; Mottainai, Nawabari, Zellij, and coding-agent packages
belong to managed generations.

The canonical appliance identity is the raw disk plus its manifest. Verification
fails closed on identity or digest mismatch. Managed package identities, where
retained in historical release metadata, are not claims about base-closure
contents.

Mottainai's Nix package is built directly from the tracked source in the release checkout and derives its version from that checkout's `package.json`. The installed Nix package keeps the bounded npm package file surface, but Runtime Appliance construction no longer depends on a same-version npm tarball already existing. This removes the release bootstrap cycle while keeping npm and appliance publication as separate release surfaces.

## Stable release distribution

Tagged releases publish the Runtime Appliance separately from npm. The canonical raw image is wrapped in a deterministic zstd transport envelope for GitHub Release distribution, with bounded release metadata recording compressed asset filename, format, byte size, and SHA-256 digest.

The release workflow builds from the exact tagged revision, verifies the canonical manifest, compresses the disk, verifies the transport envelope, decompresses it, and re-verifies canonical raw identity before and after GitHub Release publication. GitHub Actions artifacts remain CI evidence rather than the stable distribution surface.

The compressed asset must remain below GitHub's per-asset size limit. Publication fails closed if it does not. A separate large-object distribution surface may be adopted later without changing the canonical raw appliance contract.

## Runtime and MCP hardening

This release also tightens runtime boundaries accumulated since 0.6.0:

- `mottainai_list` produces deterministic bounded directory projections with explicit entry and UTF-8 byte ceilings, truthful truncation metadata, and bounded directory-selection memory.
- Mottainai-owned MCP tools have a reusable schema-derived validation boundary with bounded diagnostics, validation before side effects, explicit open opaque payloads, and fail-closed handling of unsupported owned schema constraints.
- Invalid upstream names containing the reserved `__` namespace separator are rejected before proxy registration, preventing ambiguous tool routing.
- CLI/runtime parsing preserves argv boundaries and rejects semantically empty or malformed inputs rather than silently widening behavior.
- Manager, retained-result, streaming UTF-8, HTTP routing, cancellation, and repository-state handling received additional bounded/fail-closed regressions.

## Authority boundaries

Mottainai remains authoritative for orchestration, runtime contracts, MCP schemas, lifecycle semantics, and bounded evidence projection. Nawabari remains authoritative for physical Git/worktree/session/claim state. gh-inari remains the governed GitHub Issue/PR mutation authority.

The Runtime Appliance does not make Mottainai a VM-provider implementation. Provider lifecycle integration remains a separate boundary; the appliance is intentionally provider-independent.

## Distribution

npm continues to publish the CLI and MCP package as `mottainai@0.7.0`. The Runtime Appliance is a separate release surface and is not embedded in the npm tarball.

For the appliance, use assets attached to the matching `v0.7.0` GitHub Release and verify release metadata and canonical manifest before import.

## Compatibility

This is a pre-1.0 minor release. Existing CLI, Manager, native Harness MCP, and compression-gateway surfaces remain supported, but callers should expect stricter fail-closed validation where previously ambiguous or malformed input could pass through.

Direct managed-QEMU ownership is not part of the appliance contract. The canonical artifact is designed to be consumed by provider-specific lifecycle integrations without changing guest semantics.

## Upgrade

After publication, use `mottainai@0.7.0` for the npm surface. For VM deployment, use Runtime Appliance assets from the same `v0.7.0` release.
