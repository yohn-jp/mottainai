# mottainai 0.2.0

## Summary

Mottainai 0.2.0 is the first release intended for real Pi-backed managed
development dogfooding.

The main milestone is no longer an isolated workflow API or Manager mock. The
shipped path can compose an Issue-bound task, a Nawabari-owned worktree, a
Zellij-backed Pi session, Mottainai-managed validation and lifecycle, Nawabari
commit/push authority, and gh-inari governed pull-request creation into one
bounded workflow. The packed golden-path acceptance test reaches
`pull-request-open` and proves that raw Git/GitHub mutations do not become an
alternate authority.

This release also consolidates the work accumulated since 0.1.4 around Context
Runtime guardrails, Repository Semantics, validation reuse, Manager usability,
single-authority Git/GitHub orchestration, local Runtime foundations, and a
smaller merge-integrity CI contract.

## Highlights

### Pi-backed managed development workflow

- **Pi is a first-class Manager agent profile** (#331). Manager launches Pi in
  the exact execution context returned by the managed task authority; it does
  not invent another cwd, worktree, or process registry.
- **One-command task orchestration** (#333) adds `mottainai task run`, composing
  task creation and Manager launch without manual worktree/session handoff.
- **Managed Pi mutation guard** (#332) prevents raw Git/GitHub workflow
  mutations from bypassing Mottainai, Nawabari, or gh-inari.
- **Packed Issue-to-PR golden path** (#334 / PR #356) proves the shipped path
  reaches `pull-request-open`, preserves task/execution/Manager identity, rejects
  raw mutation, treats early agent exit as incomplete, and fails closed when a
  required companion is missing.
- The packed acceptance path uses **real Zellij and real Nawabari**. Pi, `gh`,
  and gh-inari are hermetic external-edge fixtures in that test, so 0.2.0 marks
  the start of real Pi dogfooding rather than claiming that a live Pi/GitHub run
  was already performed in CI.

### One physical Git authority and one governed PR authority

- Nawabari is the physical repository/worktree/branch/resource/mutation
  authority for managed tasks. Mottainai retains task, semantic, validation,
  lifecycle, and reconciliation responsibilities.
- The supported Nawabari contract is `nawabari.standalone-execution.v1` with
  **Nawabari >= 0.4.1**, including atomic complete-set claim replacement for
  managed write-authority transitions.
- Crash/retry hardening covers task start, commit, push, and PR creation so a
  successful external effect can be reconciled instead of blindly repeated
  (#193-#196).
- Validation resolves from the authoritative Nawabari worktree and only mints
  reusable PASS evidence when the relevant pre/post repository fingerprint is
  stable (#197/#198).
- Raw Git mutations are redirected/denied at the typed workflow boundary
  instead of deriving resource authority from arbitrary shell text (#192).
- Managed pull-request creation routes through the bounded gh-inari companion;
  Mottainai no longer keeps a direct governed-PR mutation fallback. The current
  companion contract is **gh-inari 0.2.x** for `pr.create` / `pr.get`.

### Context and validation efficiency

- Context Runtime guardrails are complete: full evidence is retained while
  agent-visible responses use deterministic bounded projections and explicit
  expansion paths.
- Dogfood evidence for the Context Runtime recorded a **95.2% reduction in
  visible bytes for verbose-success output** and **89.7% for unchanged-repeat
  output**, while the selected await/watch scenario used one outward call.
- The state-aware Validation Governor suppresses redundant managed checks when
  repository/config identity is unchanged, returns compact receipts, and fails
  conservative on uncertainty. Its representative benchmark recorded roughly
  **50% fewer executions** and **96% fewer model-visible bytes**.
- Await/watch primitives internalize short polling loops instead of repeatedly
  returning unchanged status to the model.

### Repository Semantic Control Plane

The first Repository Semantics control-plane loop is complete: TypeScript facts,
explicit semantic mutation, Symbol effects/conformance, Semantic Delta and
impact, L0-L3 review classification, verification requirements/evidence,
minimum-sufficient verification planning, bounded Agent/Review/JSDoc
projections, integrity enforcement, and a managed comment-zero dogfood slice
all consume one live semantic authority rather than independent projections.

Semantic caches/projections remain derived and disposable; downstream package
consumers do not need repository semantic metadata to run Mottainai.

### Manager, Runtime, and release confidence

- The Zellij-backed Manager evolved from the original Codex-only v0 into a
  multi-agent local execution control plane with typed Codex, Claude Code, and
  Pi profiles while keeping Zellij responsible for terminal/session UX.
- Local Runtime work establishes the explicit `mottainai runtime ensure` /
  `mottainai runtime status` authority and persistent lifecycle/security
  invariants. Runtime/QEMU platform work remains independently gated; 0.2.0
  does not claim every managed QEMU platform artifact is complete.
- CI was reduced to merge-integrity semantics rather than accumulating
  informational automation. The product-contract gate now represents the
  bounded shipped workflow/package contract.
- #355 / PR #361 removed the 15 pre-existing integration failures that had
  prevented the required product-contract job from reaching its packed
  golden-path step.
- Repository-local Inari standards validation is hermetic, and real Zellij
  no-session/ANSI output is normalized before Manager inspection.

## Using Pi after upgrading

Prerequisites for the managed Pi path include compatible Pi and Zellij
executables plus Nawabari >= 0.4.1 and the supported gh-inari companion.
Mottainai does not silently install or substitute missing companions.

From a Git repository with an Issue-bound task:

```bash
npx -y mottainai@0.2.0 task run <slug> \
  --type fix \
  --issue <issue-ref> \
  --agent pi
```

`task run` returns bounded task/execution/Manager identities. The launched Pi
session runs in the canonical Nawabari worktree. Managed commit, push, and PR
operations remain the mutation path; process exit by itself is not semantic
success.

For ordinary MCP gateway setup, existing initialization remains available:

```bash
npx -y mottainai@0.2.0 init
```

## Upgrade and compatibility

0.2.0 is a pre-1.0 minor release. The release preparation itself introduces no
new runtime migration, but the product accumulated substantial architectural
cutovers since 0.1.4:

- managed physical Git/worktree authority is Nawabari, not Mottainai's retired
  local physical ownership path;
- governed managed PR mutation is gh-inari-only and fails closed when the
  companion is missing/incompatible;
- Pi task execution requires the managed profile/guard and compatible external
  companions;
- Runtime lifecycle is under `mottainai runtime`, independent of `mottainai
  init`.

Existing configuration remains pre-1.0 and should be validated with `doctor`
after upgrade. Active legacy workflow state should follow the explicit legacy
migration/adoption path rather than being inferred from branch/path names.

## Known limitations and next hardening tranche

0.2.0 is a dogfood milestone, not a claim that all robustness work is finished.
The post-release reliability tracker is #369. In particular, #362-#368 cover
small current boundary-hardening items around upstream namespace validation,
Dashboard/Manager HTTP error handling, subprocess termination fallback,
crash-safe raw config replacement, and bounded managed-process retention.
These are intentionally follow-up fixes rather than 0.2.0 release blockers.

The packed Pi golden path proves the orchestration contract with hermetic Pi and
GitHub edges. The immediate post-release validation should therefore be a real
Pi task against a small Mottainai hardening Issue. Any failure in that run is a
product defect to fix, not a reason to return to fixture-only development.

## Release procedure

This repository change only prepares version metadata and documentation. After
the release PR is merged, create the `v0.2.0` tag / GitHub Release from the
merged `main`. The tag/publication step is deliberately not performed by the
release-preparation PR.
