# mottainai 0.1.2

## Summary

Distribution and initialization hardening release. An external audit of
"0.1.0/0.1.1 unusable via `npx`" reports found the `chmod`/exec-bit theory to
be a misdiagnosis — npm links `bin` entries as executable at install time
regardless of the tarball's permission bits, and no npm bin execution
failure was ever confirmed. The real, verified problem was different: `init`
registration commands never carried an absolute `--config` path, so a
registered client server started from a working directory unrelated to the
one `init` ran in could fail to resolve `mottainai.config.json` and report a
closed connection. This was made harder to isolate than it should have been
because no test ever installed the packed npm tarball and ran the resulting
binaries — the CLI tests that existed all ran `tsx src/index.ts` directly, a
different code path from what `npx` actually executes. 0.1.2 fixes the
registration bug, closes that packed-tarball test gap, hardens `init
--import` secret sanitization, and makes explicit client-registration
failure a real CLI failure.

## Highlights

- Client registration commands are self-sufficient regardless of the
  launching MCP client's working directory.
- A packed-tarball smoke test now installs the real npm package and runs
  both `mottainai` and `mtnai` through their npm-generated launchers
  (including the Windows `.cmd` shim) before every publish.
- Import-time secret sanitization is deny-by-default instead of
  partially redacting.
- `package.json` is CLI-only: `bin` paths are normalized and unused
  library-style `main`/`types`/`exports` fields are removed.

## Fixed

- **Client registration no longer breaks after `init`**: the registration
  command `mottainai init` prints and runs for `--client claude`/`--client
  codex` now appends `serve --config <absolute path>` explicitly. Verified
  by a regression test that captures the real argv `registerClient` sends
  to a client binary and replays the captured `serve --config <path>` tail
  from an unrelated working directory with `MOTTAINAI_CONFIG` unset.
- **Explicit client registration failures now fail the run**: `mottainai
  init --client claude`/`codex` sets `summary.ok = false` and exits
  non-zero if the client binary is missing, `mcp list` fails, or the
  registration command itself fails. `--client none`, `--no-register`, and
  `--dry-run` are unaffected.
- **Registration command display no longer breaks on paths with spaces**:
  the printed/JSON `registrationCommand` now quotes the `--config` path
  when it contains whitespace or double quotes, so the command can be
  copy-pasted as-is. The registration process itself was never affected by
  this (it spawns the client with an argv array, not a shell string), but
  the string shown to the user was misleading for such paths.

## Security hardening

- `init --import` secret sanitization is deny-by-default: a URL is only
  imported if it is a plain `http:`/`https:` URL with no userinfo, query
  string, or fragment; any other scheme, or any userinfo/query/fragment
  data, rejects the whole registration.
- Argument lists containing any credential-like token (`--token`,
  `--token=...`, `Authorization: Bearer ...`, etc.) reject the entire
  upstream registration instead of silently dropping a `--flag`/value pair
  and importing a mangled argument list.
- Covered negative cases: URL userinfo, URL query string, URL fragment,
  non-http(s) schemes, `--token secret`, `--token=secret`, `Authorization`
  headers, API-key-style headers, and other credential-like arguments.

## Distribution verification

- `scripts/smoke-test.mjs` packs (or accepts a pre-built tarball via
  `--tarball`), installs it into an isolated temporary directory, and runs
  the installed `mottainai`/`mtnai` launchers from `node_modules/.bin`
  (including the Windows `.cmd` shim) — not just the raw bin target files.
  It also exercises `init --json` and the bare stdio entry point, including
  the missing-configuration exit code and stderr guidance, and asserts
  stdout stays clean of anything but the MCP protocol.
- CI (`ci.yml`) runs this smoke test on Ubuntu and Windows across Node 22
  and 24, plus a dedicated Windows job for `src/init.test.ts`.
- The publish workflow (`publish.yml`) packs the tarball exactly once,
  uploads it as an artifact, smoke-tests that exact artifact across the
  same OS/Node matrix, and publishes that same tarball — it does not
  rebuild or re-pack between verification and publish.
- Publishing uses npm's OIDC Trusted Publisher flow (`id-token: write`,
  no long-lived npm token) and treats any `npm warn publish` output as a
  failure rather than a successful-with-warnings publish.

## Behavioral changes

- `init --client <client>` now exits non-zero on registration failure for
  that client (previously warning-only).
- `init --import` now rejects more upstream registrations outright instead
  of partially importing them — see Security hardening above.
- The registration command `init` prints and runs now includes
  `serve --config <absolute path>`, and quotes that path when it contains
  whitespace.

## Upgrade instructions

```bash
npx -y mottainai@0.1.2 init --yes --no-register
```

or, for an interactive setup:

```bash
npx -y mottainai@0.1.2 init
```

No configuration migration is required from 0.1.0 or 0.1.1.

## Re-registration instructions

Anyone who registered `mottainai` with an MCP client before 0.1.2 —
including by hand-copying a previous `claude mcp add ... npx -y mottainai`
command — should re-register using the form `mottainai init` now prints, so
the registration carries an absolute `--config` path:

```bash
claude mcp remove -s user mottainai
claude mcp add -s user mottainai -- npx -y mottainai@0.1.2 serve --config /absolute/path/to/mottainai.config.json

codex mcp remove mottainai
codex mcp add mottainai -- npx -y mottainai@0.1.2 serve --config /absolute/path/to/mottainai.config.json
```

Then reconnect your client (`/mcp reconnect mottainai` in Claude Code, or
restart) so it picks up the new registration.

## Breaking changes

None for configuration files: existing `mottainai.config.json` files and
`init --import` inputs are read exactly as before. Existing **client
registrations** are not automatically broken by upgrading, but a
registration created before 0.1.2 only works if the MCP client always
starts the server from the same working directory `init` ran in — see
Fixed, above. If your client can start the server from a different working
directory (a real risk for `claude mcp add -s user`), re-register using the
command 0.1.2's `init` now prints; see Re-registration instructions.

## Known limitations

- No OS-level sandbox for `mottainai_exec` yet (tracked separately, not a
  0.1.2 scope item).
- Test architecture, coverage policy, and CI-enforced coding/architecture
  standards remain informal — tracked under the quality-assurance epic
  [#20](https://github.com/yohn-jp/mottainai/issues/20) and its sub-issues:
  layered test architecture and coverage policy
  ([#21](https://github.com/yohn-jp/mottainai/issues/21)), black-box MCP
  protocol/lifecycle conformance tests
  ([#22](https://github.com/yohn-jp/mottainai/issues/22)), deterministic
  fault-injection tests for I/O and process boundaries
  ([#23](https://github.com/yohn-jp/mottainai/issues/23)), mutation and
  property-based test effectiveness measurement
  ([#24](https://github.com/yohn-jp/mottainai/issues/24)), CI-enforced
  coding standards and architecture boundaries
  ([#25](https://github.com/yohn-jp/mottainai/issues/25)), TDD evidence and
  path-aware quality gates
  ([#26](https://github.com/yohn-jp/mottainai/issues/26)), and reproducible
  runtime build identity/diagnostic evidence
  ([#27](https://github.com/yohn-jp/mottainai/issues/27)).
- Client registration verification in CI covers Claude Code and Codex
  binaries faked for the test harness; it does not run against the real
  Claude Code or Codex applications in CI (that is done manually as part of
  post-publish verification for this release).
