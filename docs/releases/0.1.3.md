# mottainai 0.1.3

## Summary

Git workflow governance release. 0.1.2 shipped as a distribution/init
hardening patch while 172 commits of workflow-engine work accumulated
unpublished on `main` (Issue #34's family: policy schema, repository
identity, SQLite-backed task state, protected-branch decisions, and the
task/worktree lifecycle tools themselves). 0.1.3 is a straight version bump
to publish that work — `mottainai_workflow_policy_explain`,
`mottainai_workflow_task_start`, and `mottainai_workflow_task_status` are
now reachable as MCP tools (opt-in via `gateway.workflowTasks: true`) for
the first time on npm. Alongside the workflow engine, this release also
publishes the read governor, burst budget, context/result response
budgets, symbol-first semantic IR, and the retirement of native Windows
support that landed since 0.1.2.

## Highlights

- **Git workflow task engine** (Issue #34): `.mottainai/workflow.json`
  policy schema with built-in presets and authority-based weakening
  guards, repository identity resolution, a SQLite-backed
  `WorkflowStateStore`, protected-branch policy decisions, fail-closed
  repository-state detection, pre-commit/pre-push hook generation with
  bypass detection, and the dedicated `.mottainai/worktrees` task/worktree
  lifecycle (reserve → branch → activate). Exposed as three MCP tools,
  gated off by default behind `gateway.workflowTasks`.
- **Read governor**: progressive source-disclosure policy for
  `mottainai_read`, with matching CLI and VS Code surfaces.
- **Burst budget** (#73): connection/session-level aggregate budget
  layered on top of `responseBudget`, off by default.
- **Context/result response budgets** (#71): enforceable final-response
  token budgets per tool/capability/profile.
- **Symbol-first semantic IR** (#48, #84): repository semantic project
  viewer and symbol-first intermediate representation for code search.
- **Await/watch primitives** (#74): `exec_start`/`exec_await` and
  `gh_checks_await`, with a single policy-controlled polling-interval
  ceiling.
- **Content-identity dedupe** (#75): context-runtime git subprocess
  bounding with telemetry-contract-compatible result deduplication.
- **PR agent integration** (#104): configurable `pr-agent` model override
  via repository variable.
- **Native Windows support retired** (#88): WSL2 is now the supported path
  on Windows; CI and smoke tests dropped the native-Windows matrix.
- **QA architecture foundations** (#20 epic, #21/#22): layered test
  architecture, coverage policy, and black-box MCP stdio protocol tests.

## Fixed

- Worktree creation collision/race conditions now resolved atomically,
  with the atomic reserve step as the sole source of the collision reason
  (#106, #107).
- Task worktree paths canonicalized after merge so `startTask` fixtures
  receive correct `branchType`/`issueRef` (#102, #103).
- Advisory workflow decisions carry their own reason code instead of
  reusing an unrelated one.
- Repo-state detection fails closed on incomplete/partial git command
  output instead of assuming a clean state.
- `recordPullRequest` TOCTOU closed, with hardened tests and tighter
  types (#100).
- CodeRabbit review findings addressed across the read-governor VS Code
  surface (#82) and semantic IR validator's authority/integrity
  fail-open gaps (#95).

## Behavioral changes

- `mottainai_workflow_policy_explain`, `mottainai_workflow_task_start`,
  and `mottainai_workflow_task_status` exist as MCP tools but remain
  **unpublished (empty tool list) unless `gateway.workflowTasks: true`**
  is set in `mottainai.config.json` — this is a dogfooding-only exposure
  per Issue #34's non-goals (no commit/push/PR/cleanup enforcement yet).
- `mottainai_workflow_task_start` always creates a dedicated worktree/
  branch under the canonical `.mottainai/worktrees` root; it never repoints
  the current branch (including `main`) to become the work branch.
- Native Windows (`win32`) is no longer supported; `resolveStateDir` and
  related paths throw instructing WSL2 use.

## Upgrade instructions

```bash
npx -y mottainai@0.1.3 init --yes --no-register
```

or, for an interactive setup:

```bash
npx -y mottainai@0.1.3 init
```

No configuration migration is required from 0.1.2. To use the new
workflow-task tools, add to `mottainai.config.json`:

```json
{
  "gateway": {
    "workflowTasks": true
  }
}
```

then reconnect your MCP client so it picks up the newly published tools.

## Breaking changes

None. Existing `mottainai.config.json` files continue to work unchanged;
`workflowTasks` defaults to `false` (tool family stays unpublished) exactly
as it did in source before this release.

## Known limitations

- Workflow-task tools are observation/dogfooding only: no commit, push,
  PR, or cleanup enforcement is wired to them yet.
- No OS-level sandbox for `mottainai_exec` yet.
- QA epic ([#20](https://github.com/yohn-jp/mottainai/issues/20)) is
  partially complete: layered test architecture and black-box MCP stdio
  tests shipped; fault-injection tests
  ([#23](https://github.com/yohn-jp/mottainai/issues/23)), mutation/
  property-based effectiveness measurement
  ([#24](https://github.com/yohn-jp/mottainai/issues/24)), CI-enforced
  coding standards ([#25](https://github.com/yohn-jp/mottainai/issues/25),
  landed as #59 — verify CI enforcement before closing), TDD evidence
  gates ([#26](https://github.com/yohn-jp/mottainai/issues/26)), and
  reproducible build identity evidence
  ([#27](https://github.com/yohn-jp/mottainai/issues/27)) remain tracked
  separately.
