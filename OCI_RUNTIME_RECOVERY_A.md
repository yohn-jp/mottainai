# Rootless OCI recovery evidence (Wave 1)

**Result: FAIL / DECISION_REQUIRED.** The default rootless Debian container runs Nawabari 0.14.0 and creates a session, but strict session execution fails while Bubblewrap mounts `/proc`. A direct nested user/mount/PID namespace probe fails with the kernel diagnostic `VFS: Mount too revealing.` The OCI configuration masks or makes read-only 15 proc paths. No mask change or privilege expansion was tested. The conditional two-session, filesystem-isolation, and resource-enforcement checks remain **BLOCKED** because the mandatory strict launch did not succeed.

## Target and OCI baseline

The accepted target was `nixos-dev`, NixOS 26.05 x86_64, Linux `6.18.52`, VMware, systemd `260.4`, cgroup v2, UID 1000 / GID 100. The pinned Nix package set was nixpkgs revision `39ad350a0602fa0a58a544344e3e9187526ea45c5`, Podman `5.8.8`, and crun `1.30.1`. The rootless prerequisites were present: `/etc/subuid` and `/etc/subgid` each contain `sophia:100000:65536`; `user@1000.service` reports `Delegate=yes`; and a host-side `unshare -Ur true` succeeds.

The image was `docker.io/library/debian@sha256:eb593cf2c358cacef45ca0a424bbc7d30cfa3466265fc2662b9466a0ca6ba1c5` (amd64 repo digest `sha256:d405c1e1d9eecbf30022d23766a0eea235e7f499aa33e357dfd29271a839f82a`, image ID `787cd32c15da653c63f8689246f8199870afdbe8d822b7e560d651e20d6def02`). Image signature verification was **not** performed: the approved temporary policy rejected by default and accepted only `docker.io/library/debian`. The probe did not edit that policy.

Podman created a rootless, nonprivileged container with its default seccomp profile, private PID namespace, and no added or dropped capabilities. The demonstration limits were 512 MiB memory, one CPU, and 128 PIDs; these are probe settings, not product thresholds. The saved OCI config SHA-256 was `3e61e7a5378b1b795357b1d19f4fe7ade617851904cb94887f7c0d8f4634d1a4`. Its namespace list contains mount, PID, IPC, UTS, network, and cgroup namespaces; it has no user namespace entry and no OCI `uidMappings` or `gidMappings`. In-container `Seccomp: 2`; effective/permitted/bounding capabilities were `00000000800405fb`, with no `CAP_SYS_ADMIN`. The OCI process has `NoNewPrivs: 0` under Podman defaults.

The OCI config's proc masks are `/proc/acpi`, `/proc/kcore`, `/proc/keys`, `/proc/latency_stats`, `/proc/sched_debug`, `/proc/scsi`, `/proc/timer_list`, `/proc/timer_stats`, and `/proc/interrupts`. Thus the outer OCI limits are configured and visible, but no delegated writable per-session cgroup was available. Nawabari's managed-execution readiness was false with `process_tracking` required.

## Reproduction and cause

The actual package was Nawabari `0.14.0`, installed in the disposable Debian container using official Node.js `24.17.0` (archive SHA-256 `ab343a1b747c7cbf3630dfd7dbf818c5423fab2eb4f5ad1afc896f6bd121a917`). The container checkout is a named `main` branch at the accepted base revision. An unconfigured `nawabari doctor --json` reports `RUNTIME_MATERIALIZATION_MISSING` because no Node candidate was supplied. The canonical FHS materialization was then made explicit through Nawabari's documented executable variables: `NAWABARI_FHS_NODE_EXECUTABLE=/opt/node-v24.17.0/bin/node`, `NAWABARI_FHS_GIT_EXECUTABLE=/usr/bin/git`, and `NAWABARI_FHS_LS_EXECUTABLE=/usr/bin/ls`. With those values, `doctor` reports `sandbox.ready=true`, `strict_ready=true`, and runtime `fhs`. Its namespace readiness probe uses `--ro-bind / / true` without mounting proc. It also marks Landlock unavailable (`abi=null`, reduced-defense), and managed execution unavailable (`process_tracking` required; `sandbox_ready_is_sufficient=false`). Session creation succeeds. The real public command `nawabari --json session run --session <created-id> -- /bin/true` exits 3 with `SANDBOX_EXECUTION_FAILED` and `bwrap: Can't mount proc on /proc: Operation not permitted`.

The observed container ID was `571e077a85de4536f3fa6d8a11e8203a2e1d51c653ff0d86a86117c5f902ffc7`; Nawabari created session `01a123ad-c64d-7762-969d-78152d66c2cc` at base revision `152da3c3a61900fa65db8b0abce44fdcb170b73b`. The isolated Podman state directory was `/tmp/mottainai-oci-recovery-a-live.1N8JlGvu`; its OCI config was copied to the retained evidence directory before the container was removed.

Two harness attempts stopped before protected execution. The first bundle checkout was detached, so session creation returned `DETACHED_HEAD`; its unconfigured doctor result also reported `RUNTIME_MATERIALIZATION_MISSING`. After fixing the branch and explicit FHS executable candidates, a second attempt reached `strict_ready=true` and created a session but invoked `session run` from the base checkout. Nawabari correctly refused with `PROTECTED_WORKTREE`. Both were harness invocation errors, not runtime results or product fixes. The final reproducer reads the created session's worktree, verifies it equals `/workspace/.nawabari/worktrees/mottainai-$SESSION_ID`, and invokes the public command there.

An independent in-container `unshare --user --map-root-user --mount --pid --fork ... mount -t proc proc <empty-private-dir>` probe failed under the same default OCI profile with `fsmount() failed: VFS: Mount too revealing.` The child had a full capability set within its nested user namespace while seccomp remained active (`Seccomp: 2`). The equivalent host user/mount/PID namespace proc mount succeeded with seccomp disabled in the new host namespace. This narrows the observed failure to the nested procfs mount, rather than failure to create user namespaces. The kernel documents that procfs mounts in a user namespace are restricted when existing proc entries are hidden by other mounts; Nawabari/Bubblewrap requests a default proc mount without `subset=pid` ([kernel procfs mount restrictions](https://cdn.kernel.org/doc/html/latest/filesystems/proc.html#mount-restrictions)). The OCI proc overlays provide the corresponding hidden entries. No per-path comparison was run, so this is the narrowest measured cause, not proof that one specific path alone is sufficient.

The pinned Nawabari release's `dist/domain/sandbox-launcher.js` builds the strict command with user, PID, IPC, and UTS unsharing, capability drop, seccomp, then `--tmpfs / --dev /dev --proc /proc` (lines 1233–1251). Its sandbox readiness probe in `dist/domain/sandbox.js` (lines 130–134) omits the proc mount, explaining why `strict_ready=true` does not predict launch success. Source was inspected from the integrity-verified `nawabari@0.14.0` npm tarball: `sha512-zCPsnYBf9jyR98vZ7MtX0tZyXAI5xxhhGg540Y+8Lz2e4Wc4jJQChv5P5xyXvwsmtfazkQFSTpUN99yCjiyEvg==`.

There is no supported public process-tracking delegation seam for host Jinushi to manage protected-session processes without exposing its control socket. Nawabari 0.14.0 exports only `./state`, `./contract`, `./manifest`, and `package.json`. The internal `LocalSessionBackendOptions.managedExecutionReadiness` and session-registry callback are readiness booleans, not process launch/termination/observation transports (`dist/domain/session-backend.d.ts:10–22`, `dist/session-registry.d.ts:718–730`). The implementation checks local cgroup readiness (`dist/domain/session-backend.js:833–872`). No host socket was exposed to the container, and no cross-authority adapter was implemented.

## Repair proposal and remaining checks

Podman's documented `--security-opt=unmask=...` option ([Podman 5.8 run reference](https://docs.podman.io/en/v5.8.0/markdown/podman-run.1.html)) supports a bounded comparison. The proposed exact value is `--security-opt=unmask=/proc/acpi:/proc/kcore:/proc/keys:/proc/latency_stats:/proc/sched_debug:/proc/scsi:/proc/timer_list:/proc/timer_stats:/proc/interrupts:/proc/asound:/proc/bus:/proc/fs:/proc/irq:/proc/sys:/proc/sysrq-trigger`. It would retain rootless execution, private PID/user namespaces, default seccomp, default capabilities, and non-proc masks. It would remove current masking/read-only protection for those proc entries; in particular `/proc/sys` would become visible without its existing read-only overlay, expanding kernel-control exposure. This is a security decision, not a demonstrated repair. **DECISION_REQUIRED:** do not run this comparison or change production settings until the coordinator authorizes that exact change. Rollback would be to remove the single `unmask` option and recreate the disposable container with Podman's defaults. No unmask experiment was run.

The public API provides no supported way for the host Jinushi supervisor to own or observe processes launched inside this container without exposing a control socket or adding a new cross-authority API. That remains an independent integration blocker even if proc mounting is repaired. The following conditional acceptance checks are **BLOCKED**: two simultaneous strict sessions; sibling and host filesystem denial from a protected session; and CPU, memory, and PID enforcement for managed sessions. Observed outer container limits are configuration evidence only, not enforcement proof.
